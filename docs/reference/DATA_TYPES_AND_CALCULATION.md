# ChipChip 重要特性：統一數據類型與雙計算模式

本文件記錄使用者確立的全專案產品規則，適用於 ChipChip、ChipDraw、HTML、原生 Qt、共用核心及資料讀寫。這是必須遵循的設計規範；各欄位目前的實作與儲存範例見 [JSON 儲存規格](JSON_STORAGE.md)。

## 一、基本原則

先統一數據類型，再整理視圖選項及其控件。平台只負責輸入與呈現，不得各自重新定義量、單位、比例或計算語意。

必須分開處理：

1. 資料表示：整數、浮點、分欄位角度、比例兩端等。
2. 量的語意：物理長度、虛擬長度、角度、色道量，以及各自的單位與參照。
3. 計算模式：無計量計算（比特計算）或有量綱計算（物理計算）。

底層使用浮點儲存某個數值，不代表該值可以失去單位。比特計算也不構成將比例降為無量綱純量的理由。

## 二、長度類型

| 類別 | 定義 | 單位例子 |
| --- | --- | --- |
| 物理長度 | 具有物理長度意義的量 | mm、cm、m、inch 等 |
| 虛擬長度 | 像素空間中的長度 | px |

### 物理長度

- 必須具有明確的單位身份；標準代碼與本地化名稱分開。
- 不同物理單位透過共用計量模塊換算。
- 顯示單位與精度的變更不得靜默改寫幾何資料。
- 單位可由既有公開上下文明確給出，不要求在每個數值旁重複新增單位欄位。

### 虛擬長度

- px 不得直接當成 mm、inch 或其他物理長度。
- 必須明確區分介面邏輯 px、顯示器實體 px；影像像素若涉及運算，也必須識別其空間。
- 不同像素空間之間的轉換必須有明確關係，不能僅因名稱都是 px 就直接相等。
- px 與物理長度的轉換需要相應縮放率、顯示器密度或校準資料，不能採用未聲明的固定 DPI。

## 三、角度類型

角度具有不同表示種類，禁止全部壓成無區別的浮點型。

| 表示 | 數據要求 |
| --- | --- |
| 360 度制 | 浮點量值，明確為度 |
| 弧度制 | 浮點量值，明確為弧度 |
| 時分秒制 | 小時、分鐘、秒分欄位，整數部分與浮點部分分別定型 |

### 時分秒制

| 分量 | 類型 | 合法範圍 |
| --- | --- | --- |
| 小時 | uint8 | 0 < 小時 ≤ 12 h，即整數 1 至 12 |
| 分鐘 | uint8 | 0 ≤ 分鐘 < 60 min，即整數 0 至 59 |
| 秒 | 浮點型 | 0 ≤ 秒 < 60 s，且為有限值 |

- 小時 0、分鐘 60、秒 60 均不是合法歸檔值。
- 秒允許小數；禁止將三個分量都改成浮點。
- JSON 本身沒有 uint8 型別，讀寫邊界仍須驗證整數性、位寬與業務範圍。
- 不得將時分秒分量只合併成一個浮點數而丟棄表示種類。
- 時分秒在此為角度表示，不能默認解讀為日期時間或時區。
- 進位、借位、零方向、正向、跨圈、方向角與多圈旋轉量的區別，須由共用角度規則明確定義；本文件不擅自補定尚未確認的運算細節。
- 浮點的實際位寬及跨語言編碼須在實作契約中統一，本次不自行指定。

## 四、比例類型：嚴禁無量綱純量

**比例只按單量綱比例或雙量綱比例表達。嚴禁將比例定義、保存或交換為無量綱純量，尤其禁止純量縮放倍率。**

比例必須保留兩端的量、單位及用途。分母不得為零。即使相同單位在數學上可約去，也不得因此抹除比例的量綱及語意。

### 單量綱比例

兩端具有相同量綱。

使用者指定的例子：**透明比 bits : bits，按照色道量稀釋比。**

- 保留兩端色道量及 bits 單位。
- 不得以單一 0 至 1 浮點 alpha 取代權威比例資料。
- 不得將色道量與色道編碼位深混為同一概念。
- 色道量的分子／分母角色、稀釋方程及各色道處理方式，須在色彩運算規則中明確定義，不從比例範例自行猜測。
- 呈現端需要的 alpha 可由已定義規則計算，但它是呈現衍生值，不能反向取代原始透明比。

### 雙量綱比例

兩端具有不同量綱。

使用者指定的核心例子：**視圖縮放率 px : 物理長度**，例如 120 個介面 px 對應 10 mm 文件長度。

- 必須保留 px 所屬空間及物理長度所屬參照。
- 不得僅保存 zoom = 1.5、scale = 12 等裸數值。
- 百分比、倍數等畫面表示不能成為丟失量綱的理由；其基準必須可追溯。
- 實作內部的數值係數僅能是帶型別量運算的受控中間結果，不能作為獨立的權威縮放率資料或對外接口。

## 五、必須能計算顯示器上的物理量

縮放模型必須能結合介面、各個顯示器的 DPI／校準資訊及縮放關係，計算文件量在螢幕上的實際物理尺寸。

需要明確的三段關係：

| 關係 | 單位及參照 |
| --- | --- |
| 視圖縮放率 S | 介面 px : 文件物理長度 |
| 像素空間轉換 C | 顯示器實體 px : 介面 px |
| 顯示器物理密度 D | 顯示器實體 px : 螢幕物理長度，例如 px/inch |

沿單一軸向，單位相容時：

螢幕物理長度 = 文件物理長度 × S × C ÷ D

例如：

- 文件長度：10 mm。
- S：120 介面 px : 10 mm 文件長度。
- C：2 顯示器實體 px : 1 介面 px。
- D：200 顯示器實體 px : 1 inch 螢幕長度。
- 顯示結果：120 介面 px → 240 顯示器實體 px → 1.2 inch，即 30.48 mm 螢幕物理長度。

### 顯示器與縮放資料要求

- 每個顯示器分別取得及維護所需資料，不能以全域固定 DPI 代替。
- X、Y 密度及有效像素轉換若不同，必須分軸計算；旋轉等情況依完整座標變換處理。
- 系統的介面縮放 DPI 與顯示器實際物理像素密度必須區分，不得重複套用同一縮放。
- 顯示器識別、密度來源、校準依據及有效性必須可追溯。
- 移動視窗、更換顯示器或改變縮放後，更新有效換算關係。
- 視圖跨越多個顯示器時，按各區域所屬顯示器換算。
- 缺少可靠物理密度時，明確表示未知或估算，不能假稱已取得精確物理尺寸。
- 顯示器校準資料不可被默默當成文件幾何單位。

## 六、兩種計算模式

### 無計量計算（比特計算）

按資料的位元表示與編碼規則進行計算，不執行物理單位換算。

每個運算必須明確定義：

- 輸入及輸出的表示類型與位寬。
- 有符號或無符號。
- 整數、浮點或其他明確編碼。
- 合法輸入範圍。
- 溢位、下溢、截斷、捨入及錯誤處理。
- 位元組交換時所需的編碼與順序。

不能自行假設回繞、飽和或截斷。無計量計算不等於把原資料改成無量綱；比例的兩端資料與語意仍須完整保留。

### 有量綱計算（物理計算）

按量的意義、量綱、單位與明確換算關係進行計算。

每個運算必須明確定義：

- 輸入量、輸出量的類型及單位。
- 相加、相減、比較所需的相容性。
- 乘除產生的量綱及參照關係。
- 單位換算依據。
- 涉及 px 時的像素空間及顯示器／視圖關係。
- 精度、修約及無法換算時的處理。

缺少必要換算資料時不能只取數字繼續算。數值相同但單位或參照不同，不代表同一個量。

### 模式邊界

- 運算接口必須明確其計算模式，禁止隱式切換。
- 比特表示與物理量之間須有明確的解碼／編碼及單位映射。
- 單純改變變數名稱或加上顯示單位，不構成合法轉換。
- 模式是運算契約，不要求在每個既有物件新增計算模式欄位。

## 七、HTML、Qt 與儲存的一致性

- 共用同一套類型語意、驗證、單位換算、角度規則及計算契約。
- 沿用既有 ChipQuantity、ChipViewport、ChipUI.measurements 與共用計量組件，缺少能力時在共用層擴充。
- 不保存 HTML 控件索引、Qt 原生物件或本地化單位名稱代替資料身份。
- 既有公開上下文可以提供單位；不得為重複描述而擅自增加資料層、欄位或歸檔複雜度。
- 本文件定義語意與約束，不將對話中的示意 JSON 直接升格為新文件格式。
- 舊資料遷移須先辨識原單位與基準；資訊不足時明確報告，不可憑空補上量綱。
- 視圖控制與操作控制分開：吸附開關、吸附目標及吸附容差不屬於視圖控制。

## 八、後續實作驗收

1. 物理單位往返換算保留量值語意。
2. 不同 px 空間未提供關係時拒絕直接換算。
3. 時分秒逐欄驗證，邊界值符合上述範圍。
4. 單量綱比例讀寫保留兩端量與單位，透明比不退化為裸 alpha。
5. 雙量綱縮放率讀寫保留 px : 物理長度，禁止裸 zoom 作為權威資料。
6. 不同顯示器密度、介面縮放及視圖縮放下，可沿完整單位鏈計算螢幕物理量。
7. 比特計算及物理計算有明確不同的運算契約，越界與缺少換算依據時行為一致。
8. HTML 與 Qt 對相同輸入得到相同語意結果，顯示格式不改寫原始資料。
